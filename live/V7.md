# Running V7 live

V7 = five signals → one composite every 12 hours → the best **three**
configurations by trailing Calmar, held together at a third of the risk budget
each, with short entries blocked while price is above a moving average.

Backtested 179.0% at −19.99% (2022-03 → 2026-08, 14.4% total risk). Read the
risk section at the bottom before sizing anything.

## The architecture question, answered

Three sleeves, three different stops, **one** account. That sounds like it needs
sub-accounts. It does not, because of one fact:

> All three sleeves read the same composite and differ only in the exponent, the
> stop, the target, the holding cap and the gate. The exponent never changes a
> sign, and every configuration flattens on a reversal and on a flat composite.
> **The sleeves are therefore always on the same side, or flat.**

So the account holds one netted position of size `|q₁ + q₂ + q₃|`, and each
sleeve's stop goes on the exchange as its **own reduce-only `STOP_MARKET`**
sized to that sleeve's quantity. Binance accepts several reduce-only stops
against one position; they fire independently and each one reduces the net by
its own sleeve. Same for the take-profits.

That matters more than it sounds. It means **protection lives on the exchange,
not inside your Python process.** If the bot dies at 3am, the stops are still
working.

## Pieces

| file | does |

| `live/fetch.py` | builds and tops up the local data store |
| `live/runner.py` | the five signals, verified to 99.28% sign agreement against the backtest |
| `live/v7_select.py` | quarterly: ranks 200 configurations, writes the top 3 to `v7_plan.json` |
| `live/v7.py` | every bar: prints the sleeve targets, the net order, and the stop ladder |

## Setup

```bash
pip install pandas numpy pyarrow
export BOOK_STORE=~/quant/data/live

python live/fetch.py seed --months 36
python live/fetch.py update
python live/v7_select.py                 # writes the current quarter's three configs
```

## The loop

**Every 12h close (00:00 and 12:00 UTC):**

```bash
python live/fetch.py update
python live/v7.py orders --equity 10000 --risk 0.08
python live/v7.py stops  --equity 10000 --risk 0.08
```

Place the net order, then replace the reduce-only stop ladder to match the new
sleeve quantities. Cancel the old ladder first — stale reduce-only orders from
a previous bar will close positions you still want.

**Every quarter (1 Jan / 1 Apr / 1 Jul / 1 Oct):**

```bash
python live/v7_select.py
```

**Rules the runner prints but does not place:** exit a sleeve when the composite
reaches exactly 0 on a 12h close, and exit a sleeve after its holding cap (14 or
21 days). Both are checked at the 12h close, not intrabar.

## Where live will differ from the backtest, and by how much

Four gaps, none of them hidden:

**The blend is modelled as three separately compounding books.** In the
backtest each sleeve runs its own simulation at `risk/3` and the three daily
return streams are summed. A real account sizes all three off one shared
equity. Within a quarter the two drift apart by at most that quarter's return,
and the segments re-base every quarter, so the error is second-order — but it is
an error, and it flatters a quarter that starts badly.

**Stops will fill better than the backtest, not worse.** The simulation resolves
stops on 15-minute bars and assumes the stop fills first whenever one bar spans
both stop and target. A real exchange stop is continuous. This is the one gap
that runs in your favour.

**The gate uses the 12h close.** If price crosses the moving average intrabar,
the gate does not notice until the bar closes. The backtest behaves identically,
so this is fidelity rather than slippage.

**Positioning data needs a long runway.** `s_posn` uses 480-bar z-windows on 4h
bars — 80 days — and the REST endpoint serves about 30. Either run `update`
daily for three months before trading, or backfill from the archive's
`futures/um/daily/metrics` files the way `research/altmetrics.py` does. Trading
on a short panel silently changes the signal.

## What is not tested

The Binance REST paths in `fetch.py` were written against the documented API but
**never executed** — the endpoints are unreachable from the environment this was
developed in. The archive path and all signal construction are verified against
real data. Check your first `update` output by hand.

`live/v7.py` itself has not been run against a live panel for the same reason.
Its signal construction is `live/runner.py`'s, which is verified; its sleeve and
gate logic is new and should be checked against
`strategies/s87_combined.py` on the same bars before it sees money.

## Risk

V7's stationary block bootstrap puts the chance of a drawdown worse than 20% at
**98%** at the 14.4% risk that produced the 179% headline, and **34%** at 8%
risk. The realised −19.99% in the backtest is a favourable draw from a
distribution whose median is worse than the limit — it is not the expectation.

At 8% risk V7 backtests at **86.2% with a −12.3% drawdown**, and that is the
setting to start from. You can always size up after you have live evidence; you
cannot un-take a 40% drawdown in month two.

Paper-trade it for a full quarter first, including one quarterly re-selection,
and compare your realised signals bar by bar against
`strategies/s87_combined.py` before committing capital.
